# SQL Tabla: Declarativa vs. Procedural

Este es un informe técnico detallado de la reingeniería del esquema de base de datos para el proyecto de gestión de perfil profesional. Este documento registra la evolución desde un modelo relacional básico hacia una arquitectura de grado empresarial, documentando los desafíos técnicos y las soluciones implementadas.

## 1. Alcance y Objetivos Técnicos

El objetivo primordial fue la **profesionalización del esquema de datos**, moviéndolo de un estado funcional inicial ("**Forma 1**") a una estructura optimizada para escalabilidad y mantenimiento ("**Forma 2**"), ejemplos:

**Forma 1**:

``` sql
CREATE TABLE profiles_contact (
    id SERIAL PRIMARY KEY,
    profile_id INTEGER REFERENCES profiles(id) ON DELETE CASCADE,
    phone VARCHAR(20),
    email VARCHAR(100) UNIQUE NOT NULL,
    created_at TIMESTAMPTZ DEFAULT now(),
    UNIQUE(profile_id)
);
```

**Forma 2**:

``` sql
CREATE TABLE "profiles_contact" (
    "id" SERIAL PRIMARY KEY,
    "profile_id" INTEGER,
    "phone" "VARCHAR(20)",
    "email" "VARCHAR(100)" UNIQUE NOT NULL,
    "created_at" "TIMESTAMPTZ" DEFAULT (now())
);

CREATE UNIQUE INDEX ON "profiles_contact" ("profile_id");

ALTER TABLE "profiles_contact" ADD FOREIGN KEY ("profile_id") REFERENCES "profiles" ("id") ON DELETE CASCADE DEFERRABLE INITIALLY IMMEDIATE;
```

### Pilares de la Transformación:

- **Estandarización SQL:** Migración de tipos propietarios (`SERIAL`) a estándares SQL:2003 (`GENERATED ALWAYS/BY DEFAULT AS IDENTITY`).

- **Integridad Referencial Avanzada:** Implementación de restricciones `DEFERRABLE INITIALLY IMMEDIATE` para permitir flexibilidad en cargas masivas de datos sin comprometer la integridad.

- **Diccionario de Datos Estricto:** Normalización de nombres para índices (`idx_`) y llaves foráneas (`fk_`), eliminando los nombres autogenerados por el motor que carecen de semántica.

## 2. Entorno de Desarrollo y Flujo de Trabajo

Se implementó un flujo de trabajo basado en **Supabase CLI**, permitiendo un entorno de *Staging* local mediante **Docker**. Esto facilitó la ejecución de pruebas destructivas y la validación de integridad antes de cualquier cambio en la base de datos de producción.

### Comandos Clave del Flujo:

- `supabase init`: Inicialización del framework de migraciones.

- `supabase db pull`: Extracción del esquema actual de producción para establecer un *baseline*.

- `supabase db reset`: Reconstrucción total del entorno local (borrado de DB, aplicación de migraciones y carga de `seed.sql`).

- `supabase db push`: Despliegue de los cambios estructurales validados hacia la nube.

## 3. Registro de Incidentes Técnicos y Soluciones

Durante la fase de migración local, se detectaron y resolvieron tres incidentes críticos que afectaban la evolución del esquema:

### 3.1. Conflicto de Generación de Identidad (Error 55000)

- **Problema:** Al intentar transformar columnas de `SERIAL` a `IDENTITY`, PostgreSQL devolvió el error: `column "id" already has a default value`.

- **Origen:** El tipo `SERIAL` es un "azúcar sintáctico" que crea una secuencia y la vincula mediante una cláusula `DEFAULT`. La cláusula `IDENTITY` es incompatible con la existencia de un `DEFAULT` previo.

- **Resolución:** Se procedió a desvincular la secuencia implícita antes de declarar la identidad.

```sql
ALTER TABLE profiles ALTER COLUMN id DROP DEFAULT;
ALTER TABLE profiles ALTER COLUMN id ADD GENERATED BY DEFAULT AS IDENTITY;
```

### 3.2. Truncamiento de Identificadores y Error de Referencia (Error 42704)

- **Problema:** Error al intentar renombrar restricciones: `constraint "..." does not exist`.

- **Origen:** El límite de identificadores en PostgreSQL es de **63 bytes**. Nombres de restricciones como `responsibilities_translations_responsibility_id_language_code_key` (67 caracteres) fueron truncados automáticamente a `..._code_k`.

- **Resolución:** Se abandonó la estrategia de renombrado (`RENAME`) por una de reconstrucción limpia. Se eliminó la restricción basándose en su existencia probable (truncada o no) y se creó un índice explícito con un nombre controlado.

```sql
ALTER TABLE responsibilities_translations 
DROP CONSTRAINT IF EXISTS responsibilities_translations_responsibility_id_language_code_key;

CREATE UNIQUE INDEX idx_responsibilities_trans_resp_lang 
ON responsibilities_translations(responsibility_id, language_code);
```

### 3.3. Fallo en Script Dinámico de Metadatos (Error 42703)

- **Problema:** El script de sincronización fallaba con `column "id" does not exist`.

- **Origen:** En el bloque PL/pgSQL, se consultaba `information_schema.columns` usando `column_name = id`. PostgreSQL interpretó `id` como un identificador de columna en lugar de un valor literal.

- **Resolución:** Corrección de la sintaxis para comparar contra un literal de texto.

```sql
IF EXISTS (SELECT 1 FROM information_schema.columns 
           WHERE table_name = t AND column_name = 'id') THEN -- Uso de comillas simples
```

## 4. Gestión de Datos Maestros y Secuencias

Una parte crítica de la memoria técnica es el manejo de la **Master Data**. Al insertar registros con IDs prefijados (1, 2, 3...), los contadores internos de las tablas quedan desalineados.

### Estrategia de Sincronización Post-Carga:

Se desarrolló un script de automatización que recorre todas las tablas del esquema `public`, identifica aquellas con columna `id` y ajusta su secuencia al valor máximo actual + 1. El uso del parámetro `false` en `setval` asegura que el siguiente valor entregado sea el correcto sin saltos.

```sql
DO $$ 
DECLARE
    t text;
BEGIN
    FOR t IN 
        SELECT table_name FROM information_schema.tables 
        WHERE table_schema = 'public' AND table_type = 'BASE TABLE'
    LOOP
        IF EXISTS (SELECT 1 FROM information_schema.columns 
                   WHERE table_name = t AND column_name = 'id') THEN
            EXECUTE format('SELECT setval(pg_get_serial_sequence(%L, ''id''), 
                           coalesce(max(id), 0) + 1, false) FROM %I', t, t);
        END IF;
    END LOOP;
END $$;
```

## 5. Conclusión de la Memoria Técnica

El esquema final presenta una **estabilidad del 100%** en las pruebas de estrés local. La base de datos de producción ahora posee:

1. **Nombres predecibles:** Facilitando el mantenimiento y la creación de queries complejas.

2. **Seguridad de Identidad:** Evitando la inserción accidental de duplicados o valores nulos en llaves primarias.

3. **Portabilidad:** Al utilizar estándares SQL, el esquema es más resiliente a futuras migraciones de motor o versiones.

Este proceso garantiza que la infraestructura de datos cumple con los estándares de arquitectura de software y gestión de sistemas críticos.
